# RCA — PRODUCTION backend slow navigation (app.surirent.sr / vastgoed-app)

## Problem statement
Kiosk on prod is slow to navigate. Trivial endpoints are slow server-side in prod but fast in preview.
Reporter numbers: `GET /api/kiosk/printers/online` (401, NO DB) TTFB 160–420 ms; `/api/public/apk/latest` (1 Mongo query) 250–720 ms; preview ~60 ms; in-process ASGI 1–2 ms.

## Live measurements I took (direct pod URL https://vastgoed-app.emergent.host, bypasses Cloudflare)
- `/api/kiosk/printers/online` (401, NO DB): **2246 ms, then 193 ms, then 871 ms** on repeated hits.
- `/api/public/apk/latest` (1 Mongo query): **4067 ms** sample.
- Frontend `/health` (served via CF worker): 780 ms.
The extreme variance (193 ms → 2246 ms → 4067 ms) on a no-DB endpoint is the signature of **event-loop / CPU contention**, not a fixed per-request cost and not DB latency.

## Confirmed root cause (evidence-backed)
1. **Single uvicorn worker per pod.** `etc/supervisor/conf.d/supervisord.conf`: `command=/root/.venv/bin/uvicorn server:app --host 0.0.0.0 --port 8001 --workers 1 --reload`. One process = one event loop per pod. 2 pods total.
2. **CPU capped at half a core.** `get_tier`: tier_1 "Launch" → cpu request 250m, **cpu_limit 500m**, mem 1Gi/2Gi, replicas 2 (fixed), hpa_enabled=false, vpa_enabled=true.
3. **That single event loop concurrently serves everything:** all HTTP, kiosk WebSockets at `/api/kiosk/ws` (presence `ping` every ~20s → each does `db.kiosk_presence.update_one`, server.py ~10215), SSE `/api/admin/events`, background loops (`_reminder_loop` 6h, `_overdue_push_loop` 15min, `_auto_invoice_loop`, `_daily_billing_checks_loop`), a `_live_sync_broadcast` HTTP middleware on every mutating request (cache clears + company_id resolve + SSE broadcast), and Brotli+GZip compression middleware on every response.
4. **CPU-bound work offloaded with `asyncio.to_thread`** (PDF via CairoSVG at lines 4107/7274/11329/etc., pywebpush at 15265) still competes for the same ≤500m CPU (GIL + cap) — when a PDF/push batch runs, the loop starves and trivial requests queue.
5. **Periodic heavy demo-reset jobs** run in-process — logs show `[demo-reset] Reset demo-omgeving demo-company-fixed-uuid-...` / `Voltooid`.
6. **Pods are healthy**: `get_pod_events` → both Running, restart_count 0, no OOMKilled/evictions. Memory is NOT the issue.
7. **Constant probe load**: k8s probe hits backend `GET /health` and gets **404** (backend has no /health route) twice per cycle — harmless but adds steady request load to the one worker.

Preview is fast (~60 ms) with the SAME `--workers 1` code because the preview pod is not capped at 500m CPU and carries almost no concurrent load (no live kiosks/WebSockets/SSE/demo traffic). The differentiator is CPU + concurrency, not app logic.

## Could NOT directly measure (flagged as inferred)
- **Pod→Atlas Mongo ping / slow queries (reporter item 3):** no shell in the prod pod, and `mongo_query` runs from tool infra (not the pod), so I cannot report a true pod→DB RTT. The apk endpoint's 250 ms–4 s spread tracks the same event-loop contention rather than isolated DB latency. INFERRED, not measured.

## High-frequency log noise (reporter item 4)
- No 5xx. `fetch_app_logs` status_counts over 120 min: 200×84, 401×6, 404×180 (the 404s are the /health probe).
- Repeating `Task exception was never retrieved` + `starlette.websockets.WebSocketDisconnect: (ABNORMAL_CLOSURE 1006)` from the kiosk WS `receive()` tasks (server.py 10346 / 10555) on every kiosk disconnect — unhandled task exceptions, noisy, minor overhead.

## Likely bottleneck (one line)
A single uvicorn worker on a 500m-CPU-capped pod, saturated by concurrent WebSocket presence writes + SSE + background loops + per-response compression + periodic demo-reset/PDF work → event-loop/CPU contention queues even trivial no-DB requests, giving the 200 ms–4 s variance.

## Fixes
- **User (tier_upgrade_needed):** Raise the tier in Deployment Panel → Resources. tier_1 caps CPU at 500m/pod with fixed 2 replicas and HPA disabled; the live workload exceeds half a core. More CPU headroom (and scaling) directly reduces the contention-driven latency spikes.
- **Code (E1):** (a) Run multiple uvicorn workers (e.g. `--workers 2–4`, sized to the new CPU) and/or move CPU-bound PDF/compression off the request path; (b) throttle/debounce the per-WebSocket `kiosk_presence` Mongo writes; (c) handle the WS `receive()` task exceptions to stop the ABNORMAL_CLOSURE traceback spam. Note: adding workers REQUIRES the tier CPU bump to help.
- **Minor:** backend has no `/health` route so the k8s probe 404s — a probe/manifest mismatch, not the perf cause.

## Note on redeploy
A plain redeploy re-runs the same source/image and does NOT fix this; it only restarts pods (temporary relief). Not performed — the fix is tier + code.
