# RCA — Regular Android phone misdetected as KT-V520 (kiosk auto-print)

**Deployment:** vastgoed-app (`app.surirent.sr` / vastgoed-app.emergent.host)
**DB read (read-only):** `vastgoed-app-vastgoed_kiosk` on active run `d9d857c7-e71a-4332-92d1-26a76cfbd976`
**Request:** diagnose only — no code change, no deploy.

## Symptom
On a regular Android phone/tablet running the APK (RN WebView), the kiosk success page does not WebSocket-print to a separate KT-V520 — the phone behaves as if it IS the KT-V520.

Frontend gate: `isKtpDevice() = apkBridge && ( window.__SURIRENT_KTP__===true || /KT-?V520|KTV520|KingTop/i.test(UA) || localStorage ktp_device_token )`

## What the data proves

### 1. NO device UA contains "KT-V520" — the UA regex branch never fires
Real printers and phones report one of two model strings, neither of which the regex matches:
- `Android 11; V520 Build/RP1A.200720.011` — model string is **"V520"**. The regex `/KT-?V520|KTV520|KingTop/i` requires a "KT"/"KTV" prefix, so bare **"V520" does NOT match**.
- `Android 12; M2102J20SG Build/SKQ1.211006.001` — **M2102J20SG is a Xiaomi Redmi Note 10 Pro**, an ordinary consumer Android phone — obviously no match.

So the `UA` branch of `isKtpDevice()` evaluates **false for every real device in the fleet.** Device detection is driven entirely by `window.__SURIRENT_KTP__` and/or the stored `ktp_device_token` — not by device identity.

### 2. `ktp_detected` tracks `paired` exactly — not the UA
In the 30 most-recent `kiosk_devices_seen` docs, every `paired:true` doc has `ktp_detected:true`, and every `paired:false` doc has `ktp_detected:false`. The determinant of "this is a printer" is the stored pairing token (`localStorage ktp_device_token` → `paired`), independent of model.

### 3. Regular Android phones (Xiaomi M2102J20SG) are flagged as KTP — the reported bug
Multiple **Xiaomi M2102J20SG** rows are `paired:true, ktp_flag:true, ktp_detected:true, rn_bridge:true`, including rows named `KT-V520 #2`, `KT-V520 #3`, and ordinary employee devices named `Otniella Pika` and `Gopi Appartements`. A regular phone that once completed pairing keeps the token in localStorage, so `isKtpDevice()` returns true on it forever → the success page treats the phone itself as the printer and never WebSocket-prints to the real KT-V520.

### 4. User hypothesis "APK sets ktp_flag on every device" is FALSE
APK devices (`rn_bridge:true`) exist with `ktp_flag:false`:
- `6ad13124` — M2102J20SG, `rn_bridge:true, paired:false, ktp_flag:false, ktp_detected:false`
- `6ad21fb0` — **SM-S938B (Samsung Galaxy S25 Ultra)**, `rn_bridge:true, paired:false, ktp_flag:false, ktp_detected:false`

So `ktp_flag` is **not** universally set by the APK. It is set when the device becomes paired — `ktp_flag:true` correlates with `paired:true` (two older V520 rows `6ad2683a`, `6ad0936f` are `paired:true` but `ktp_flag:false`). For the misdetected non-KT-V520 Android UAs the request asked about: **both `ktp_flag:true` AND `paired:true`.**

### 5. Real KT-V520 UA does NOT contain "KT-V520"
Printer rows (role=printer) report model "V520" (Android 11 build) or M2102J20SG (Xiaomi). The literal string "KT-V520" appears only in the human-assigned `name` field, never in `ua`. UA-based detection is therefore unreliable by construction.

### 6. `android_bridge` is always false
Every row has `android_bridge:false`, including APK devices — the APK bridge is represented by `rn_bridge`, not `android_bridge`. Anything keying off `android_bridge` would never trigger.

### 7. `kiosk_printers` — 29 registrations, heavy churn, only 2 active
All `name` values are manual labels `KT-V520 #1..#4`. 27 are `revoked:true`; only two are `revoked:false`:
- `KT-V520 #2` — created 2026-10-17T09:48:43Z (active, recent last_seen)
- `KT-V520 #1` — created 2026-10-16T23:24:27Z, `paper:"ok"` (active, recent last_seen)
Repeated create/revoke cycles of the same #1–#4 labels on 10-14 → 10-17 indicate repeated re-pairing — consistent with tokens landing on the wrong (non-printer) devices and being re-issued.

## Root cause
Device-role detection is token/flag-driven, not identity-driven. `isKtpDevice()`'s only reliable branch (UA regex) never matches real hardware ("V520" ≠ "KT-V520"), so detection falls back to `localStorage ktp_device_token` / `ktp_flag`. Any ordinary Android phone that once paired (or had the flag set) is permanently classified as the KT-V520 printer, so the success page prints locally instead of pushing over WebSocket to the dedicated printer.

## Suggested fix (owner: E1 / Code — frontend)
1. Fix the UA regex to match real hardware: the KT-V520 reports model **"V520"** (and some units are Xiaomi M2102J20SG). The current `/KT-?V520|KTV520|KingTop/i` matches none of them. Decide the true hardware signal — the model does not reliably identify a KT-V520, so UA alone is insufficient.
2. Stop treating a stored `ktp_device_token` / `ktp_flag` as sufficient to classify a device as the printer. The pairing token is being stored on ordinary phones; either bind the printer role to a verified hardware signal, or scope the token so a non-printer device that paired once is not permanently promoted to printer.
3. Audit the pairing flow that writes `ktp_device_token` to localStorage and sets `ktp_flag` — it is landing on employee/admin phones (M2102J20SG rows named "Otniella Pika", "Gopi Appartements").

## Data note / housekeeping (owner: User)
Several `kiosk_devices_seen` and `kiosk_printers` rows have `name:"KT-V520 #N"` but UA = Xiaomi M2102J20SG (a regular phone). Once the logic is fixed, the user should revoke stray `kiosk_printers` tokens and clear `ktp_device_token` from mis-paired phones so they stop reporting as printers.

## Not verified
Behavior is live-DB/localStorage-driven; it cannot be reproduced in an isolated sandbox (no app secrets, no device state). Findings above are from the production DB reads only.
