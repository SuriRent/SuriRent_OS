# RCA — APK FCM token niet gekoppeld ("Nog geen Android-toestel gekoppeld")

Deployment: vastgoed-app (20d2fd04-…) · active run 58d7959a-… · frontend_type=cloudflare (R2) · tier_1
Live URLs: https://vastgoed-app.emergent.host , https://app.surirent.sr (both serve the same bundle).

## Problem statement
APK meldt een FCM-token via `window.onFcmToken`, maar de webapp toont onder "Gekoppelde Android-toestellen" nog steeds "Nog geen Android-toestel gekoppeld".

## Root cause
Everything on the server + deployment side is healthy and correct: endpoint exists (`@api.post("/push/fcm/register")` writing to `fcm_tokens`), env vars present, and the served frontend bundle is recent and contains the full APK-registration logic including `window.onFcmToken`.

The failure is entirely **client/APK-side**: the registration POST is never emitted by the browser. In `frontend/src/lib/fcm-apk.js`, `register(token)` begins with `if (!valid(token)) return;` where `valid` = `/^[\w-]{10,}:[\w-]{80,}$/.test(token.trim())`. If the token does not match this regex, `register()` **returns silently — no POST, no error, no status set**. The observed signature (zero register POSTs, empty `fcm_tokens`, devices-list 200 = admin present) is exactly what you get when either:
  (a) the APK token handed to `window.onFcmToken` does NOT match the strict regex (e.g. different length/format, or wrapped/JSON), so `valid()` rejects it and the call is dropped before the network; or
  (b) `window.onFcmToken` is never actually invoked by the APK (timing: APK injects the token before the lazy AdminDashboard chunk mounts and `installFcmApk()` has defined `window.onFcmToken`, or the APK uses a delivery channel the handlers don't catch).

This is NOT a deployment, infra, manifest, secret, or data-migration problem.

## Suggested fixes
- **Code (E1):** Instrument `frontend/src/lib/fcm-apk.js` so the silent failure becomes visible and recoverable: log/surface when `window.onFcmToken` is called, log the raw token received and whether `valid()` passed, and set `status.error` on an invalid-format token instead of returning silently. Re-examine whether the regex `/^[\w-]{10,}:[\w-]{80,}$/` matches the real token format the APK emits (FCM tokens can contain characters/segments this pattern rejects); loosen/adjust if needed. Also consider buffering a token that arrives before `installFcmApk()` has registered `window.onFcmToken` (re-apply on mount). This could NOT be reproduced in the sandbox because it requires the real APK webview + a logged-in admin session (no app secrets / device in the eph pod).
- **User (test_and_verify):** In the APK webview, log in as admin, open the admin dashboard, and capture the webview console + network tab. Confirm (i) `window.onFcmToken` is actually called and with what token string, and (ii) whether a `POST /api/push/fcm/register` is attempted. If the token string is visible, check it against `/^[\w-]{10,}:[\w-]{80,}$/`. Feed findings back to E1 to finalize the Code fix.
